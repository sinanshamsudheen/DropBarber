# DropBarber Backend

## What this is

The backend for a location-based barber marketplace + shop CRM/appointment system. It is a **modular monolith** (not microservices) that will eventually implement the API described in `../docs/api.md` against the schema in `../docs/db_er.md`.

**Phase 1** built the app foundation. **Phase 2** (current) implements the full v1 data model — SQLAlchemy models, the first Alembic migration, and PostgreSQL RLS — with no business API routes yet. See "Phase 2 scope" below.

## Stack

- Python 3.11+, [uv](https://docs.astral.sh/uv/) for dependency management
- FastAPI + Uvicorn (ASGI)
- SQLAlchemy 2.x (async, `asyncpg` driver) against Supabase PostgreSQL, models via GeoAlchemy2 for PostGIS
- Alembic (async-compatible migration environment)
- Pydantic v2 / pydantic-settings for config and validation
- JWT auth via Supabase-issued access tokens (PyJWT, HS256 shared secret)
- RBAC foundation + PostgreSQL RLS (enabled + policies on every table)
- [Supabase CLI](https://supabase.com/docs/guides/local-development) for a local dev/test Postgres (Docker-backed)

|---|---|

| `JWT_AUDIENCE` | Expected `aud` claim, Supabase default is `authenticated` |
| `JWT_ISSUER` | Optional expected `iss` claim; leave blank to skip issuer verification |
| `CORS_ALLOWED_ORIGINS` | Comma-separated list of allowed frontend origins (no wildcard) |

Never commit a real `.env`. `.env.example` documents the shape only.

## Local Postgres (Supabase CLI)

Local development and testing run against a real Postgres via the Supabase CLI (`supabase` — a devDependency in the repo-root `package.json`, run through `npx`), not a mocked/sqlite database. This gives you the same `auth` schema (and its `auth.uid()` helper) that RLS policies rely on.

```sh
# from the repo root
npx supabase start   # Docker-backed local Postgres + Auth + Storage
npx supabase status   # prints the DB URL, JWT secret, Studio URL, etc.
npx supabase stop     # when done
npx supabase db reset  # wipes and recreates the local DB (re-run `alembic upgrade head` after)
```

`server/.env.example`'s `DATABASE_URL`/`JWT_SECRET_KEY` already match the local stack's defaults (`postgresql+asyncpg://postgres:postgres@127.0.0.1:54322/postgres`, and the well-known dev JWT secret `super-secret-jwt-token-with-at-least-32-characters-long`). The Supabase CLI's own migration system (`supabase migration`/`supabase db push`) is **not** used — Alembic stays the only schema authority; the CLI is purely a local Postgres provisioner.

## Alembic

```sh
uv run alembic revision --autogenerate -m "add something"
uv run alembic upgrade head
```

`alembic/env.py` builds its connection URL from `Settings` (i.e. `DATABASE_URL`), not from `alembic.ini`, so no credential is duplicated/committed. Every domain model is imported at the top of `alembic/env.py` so it registers on `Base.metadata` (`app/db/base.py`) before autogenerate can see it — add new ones there.

The Phase 2 migration (`alembic/versions/b89d0446d7c8_phase_2_schema.py`) creates the full v1 schema: 17 tables via ordinary `op.create_table`/`op.create_index` (autogenerated from the SQLAlchemy models, so metadata and schema stay in sync), plus hand-written raw SQL for everything Alembic/SQLAlchemy Core has no construct for:

- `postgis` + `btree_gist` extensions
- `shops.location`, a generated `geography(Point)` column derived from `latitude`/`longitude`
- a booking-overlap `EXCLUDE` constraint on `appointments` (GiST, `btree_gist`-backed)
- a trigger syncing `auth.users` → `public.users` on signup (`public.handle_new_auth_user`)
- a trigger validating `shop_customers.preferred_barber_id` belongs to the same shop
- Row Level Security: enabled on every table, with policies and three `SECURITY DEFINER` helper functions in a dedicated `app_rls` schema

Each of those raw-SQL statements is its own `op.execute()` call — asyncpg's extended query protocol rejects multiple `;`-separated statements in one call, so don't combine them.

## Tests

```sh

```

Covers the Phase 1 foundation (app startup, `/health` + `/health/ready`, the JWT auth dependency's accept/reject behavior, config loading/validation — `/health/ready` accepts `200` or `503` since a real Postgres instance isn't assumed) plus Phase 2's schema/RLS (`tests/test_schema.py`): 7 scenarios (customer-owns-own-data, cross-shop isolation, public read of active shops, private CRM notes blocked, etc.), run directly against Postgres by impersonating different users via `SET LOCAL ROLE` + `request.jwt.claims` (no business routes exist yet to exercise this through the API). `test_schema.py` skips automatically if `DATABASE_URL` isn't reachable — start the local stack first (see above) to actually run it.

## How authentication works

Supabase Auth issues JWT access tokens to the frontend. The frontend sends them as `Authorization: Bearer <token>`. This backend:

1. Extracts the bearer token (`app/auth/dependencies.py`)
2. Verifies signature/expiration/audience with the shared `JWT_SECRET_KEY` (`app/core/security.py`, HS256)
3. Maps the verified claims to an `AuthenticatedUser` (`app/auth/schemas.py`)

The authenticated user's identity always comes from the verified token — never from a client-supplied body field. Password/credential storage stays entirely in Supabase Auth; this backend never stores or hashes passwords.

## How RLS/RBAC fit together

Per `../docs/security.md`, authorization is layered: **Supabase Auth/JWT → FastAPI authentication → RBAC → PostgreSQL RLS**. RLS is the database-level backstop; the application layer is never the sole authorization boundary.

- **RLS** (enforced in the database, wired from `app/db/rls.py`'s `set_rls_context`): every table is `ENABLE ROW LEVEL SECURITY`, with policies keyed off `auth.uid()` — the same identity Phase 1 propagates via the `request.jwt.claims` Postgres GUC. Three `SECURITY DEFINER` helper functions live in a dedicated `app_rls` schema (not exposed to PostgREST) so policies can check shop membership without recursing into `shop_members`' own policy: `app_rls.is_active_shop_member(shop_id, roles?)`, `app_rls.shop_id_for_barber_profile(id)`, `app_rls.shop_has_any_member(shop_id)` (the last one exists solely to let a shop's very first member insert themselves as `owner` — otherwise no membership row could ever be created). RLS is coarse: it enforces *shop-boundary* membership, not fine-grained permission strings.
- **RBAC** (`app/permissions/`): `Role` and `Permission` plus the `ROLE_PERMISSIONS` mapping and `require_role`/`require_permission` dependency factories exist as pure data/shape from Phase 1. Resolving *which* role the current user holds *for a given shop* (`get_current_shop_role` in `app/permissions/dependencies.py`) is still a deliberate `NotImplementedError` — `shop_members` now exists, but wiring this up needs an actual route/shop_id context, which is Phase 3.

## Phase 2 scope

Implemented: the full v1 schema from `docs/db_er.md` as SQLAlchemy models, organized by domain (`app/{users,customers,shops,staff,services,availability,appointments,points,media,reviews}/models.py`); the first Alembic migration (17 tables, all constraints/indexes, the booking-overlap exclusion constraint, the `auth.users` sync trigger, and RLS); a local dev/test Postgres via the Supabase CLI; schema/RLS verification tests.

**Not implemented (intentionally deferred to Phase 3):** any business API routes (shop/barber/service/appointment/customer/review/points/media CRUD), booking/availability calculation logic, shop-membership-based role resolution (`get_current_shop_role`), frontend integration, and — per the product spec — payments/branches/loyalty/messaging/inventory/payroll entirely.
